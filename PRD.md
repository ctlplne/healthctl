Build a self-hosted clinical history and provisional diagnosis tool

Mission

Act as the senior engineer responsible for implementing this application in the current repository. Build a working product, run it, exercise its workflows, and fix meaningful failures. Do not stop after a plan, scaffold, architecture diagram, or static mockup.

The product is a self-hosted, model-agnostic clinical interview application. It takes an adaptive medical history, lets the user review and correct that history, and shows a provisional differential diagnosis generated by their configured model. Every assessment is prominently experimental, AI-generated, and not reviewed by a healthcare professional.

User-visible diagnostic estimates are a core requirement. Preserve them throughout implementation. A user may review the estimate before visiting a physician; the application should produce a useful report to bring to that visit. It must also be able to explain when there is insufficient information to generate a useful estimate.

The developer distributes software and does not operate a hosted clinical service. Support OpenAI, Anthropic Claude, and bring-your-own-model endpoints, including local inference. Use Business Source License 1.1.

Use “healthctl” as the configurable default display name. Do not invent a legal company name, professional endorsement, or clinical validation.

1. Working approach

Inspect the repository, applicable AGENTS.md instructions, installed tools, and existing conventions first. Preserve unrelated work. If this is an empty repository, create the application here. Otherwise integrate carefully and explain any necessary architectural adjustment.

Choose reasonable implementation defaults and proceed. Record assumptions and unresolved release decisions in documentation. Ask only about a genuinely blocking ambiguity. Product naming, visual styling, and missing API credentials should not block implementation.

Use parallel agents for genuinely independent implementation or review work if available. Coordinate ownership of shared files and integrate their work yourself.

Make changes locally. Do not publish, deploy publicly, purchase services, send messages, or push commits without authorization. Use synthetic clinical data for development and tests.

Write a short execution plan, then implement immediately. Maintain a concise progress file so work can resume across context limits. A final delivery must distinguish implemented features, verified behavior, unavailable live checks, and remaining limitations.

2. Architecture and scope

Prefer this stack unless the existing repository provides a compelling alternative:

* Go backend with a modular monolith architecture.
* PostgreSQL with versioned migrations.
* React, TypeScript, and Vite frontend.
* Docker Compose for a reproducible local deployment.
* Backend-served frontend assets, with minimal runtime services.

Organize the backend into interview orchestration, clinical state, safety policy, assessment generation, provider adapters, persistence, authentication, and exports. Use typed interfaces and versioned schemas.

Begin with one authenticated owner per installation. This is a personal deployment, not an anonymous public medical service. Enforce authorization on every clinical and export endpoint. Design data ownership explicitly so later multi-user support is possible; do not implement enterprise tenancy now.

The initial clinical scope is adult, English-language, text-based symptom interviews. Collect age and relevant clinical context explicitly. Clearly identify unsupported populations or situations and provide an incomplete history report when appropriate; do not pretend the adult workflow is validated for children or pregnancy-specific care.

Initial exclusions: prescribing, medication changes, autonomous test ordering, image interpretation, voice, EHR integrations, billing, subscriptions, Kubernetes, and clinical signing workflows. Keep extension points without building these features.

3. Complete user journey

Implement this full workflow:

1. Start the application and create the owner account without default credentials.
2. Configure the model provider and test connectivity using nonclinical input.
3. See which provider receives interview content and acknowledge the experimental-use notice.
4. Start an encounter with a chief concern and relevant background.
5. Complete an adaptive interview with free text and optional answer choices.
6. Pause, resume, revise earlier answers, and review the captured history.
7. Confirm that the summary represents what the user reported.
8. Generate and view an experimental provisional differential diagnosis.
9. Download versioned JSON and print a polished report using browser Save as PDF.
10. Reopen the encounter, add information, regenerate the assessment, or delete the encounter.

Make all controls functional. Include clear loading, empty, incomplete, failure, retry, outdated-assessment, and unsupported-scope states.

Use a calm, readable medical interface with responsive mobile and desktop layouts. Provide keyboard access, associated input labels, accessible status messages, and sufficient contrast. Avoid fake confidence gauges, “all clear” badges, and decorative dashboards that obscure the interview.

4. Self-hosting and data boundaries

No developer-hosted control plane, central account, license callback, required telemetry, remote transcript collection, third-party analytics, tracking scripts, or remotely loaded fonts.

User data resides in the operator’s deployment. If a cloud model is selected, clearly explain that relevant clinical content is transmitted to that provider. Never advertise cloud inference as fully local or imply that self-hosting prevents all third-party data processing.

Local inference must work without an internet connection once software and model dependencies are installed. Bundle UI assets. Do not silently contact a cloud provider when a local model fails.

Keep provider credentials server-side, preferably in environment variables or Docker secrets for the MVP. Show connection status and masked configuration in the UI; do not return stored secrets to the browser.

5. Model adapters

Implement real adapters for:

* The current supported OpenAI API.
* The current supported Anthropic Claude API.
* An explicitly configured OpenAI-compatible endpoint for compatible local or remote inference servers.

Check official provider documentation when implementing; do not invent API behavior, hardcode an assumed current model name, or treat every compatible endpoint as feature-identical. Model identifiers must be configurable.

Define a shared application contract for interview turns and assessments. Record provider, requested model, returned model/version when available, relevant settings, prompt version, schema version, and application version.

Support capability differences. Use native structured output where available; otherwise use constrained prompting and strict server-side parsing. Validate semantics, required fields, enums, lengths, evidence references, and allowed actions. Attempt at most one bounded repair before displaying a recoverable failure.

Use bounded timeouts, cancellation, transient retries, response limits, and token budgets. Preserve completed user input if a call fails. Never substitute demo results, switch providers, or send clinical data to an additional endpoint without explicit operator configuration and disclosure.

Provider changes must be visible and audited. A stored assessment continues to identify the provider that actually generated it.

Include an obviously labeled synthetic demo mode that requires no API keys and uses a separate demo database or clearly isolated records. Demo results must never be presented as live inference. Missing credentials in real mode should produce setup instructions, not canned diagnoses.

6. Application-owned interview state

The application owns state and permitted transitions. The model proposes structured changes; it cannot directly modify arbitrary records, alter access controls, execute code, fetch URLs, or invoke external tools.

Use a state machine such as intake, interviewing, history_review, assessing, assessment_ready, needs_clarification, interrupted_for_safety, and failed_recoverably. Track urgency separately so an assessment cannot clear an unresolved warning.

Persist transcript messages, questions, answers, clinical facts, contradictions, outstanding questions, summary revisions, assessment versions, acknowledgments, and minimal audit events.

Use encounter revisions and idempotent submissions or optimistic concurrency control. Refreshing, double-clicking, retrying, reconnecting, or receiving a late model response must not duplicate turns, overwrite newer answers, or attach an assessment to the wrong history.

Use structured state with relevant original evidence and bounded recent dialogue for model context. Do not repeatedly summarize summaries until provenance disappears. Handle context limits explicitly.

7. Clinical fact integrity

Each finding should capture:

* Concept and original user wording.
* Status: reported_present, explicitly_denied, unknown, not_asked, uncertain, or declined.
* Value and units when relevant.
* Symptom time context, separately from message timestamps.
* Source type, message or answer identifier, and exact supporting text span.
* Confirmation and correction status.
* The version and finding it supersedes, where applicable.

An unanswered, skipped, vague, or unmentioned symptom must never become a negative finding. Do not turn “otherwise fine” into a long fabricated review of systems. Do not invent normal vital signs, examination findings, test results, medication doses, or precise dates.

Distinguish present symptoms, past symptoms, family history, and statements about someone else. Preserve unresolved contradictions until clarified. Medication and allergy uncertainty must remain explicit.

Keep model interpretations in the assessment layer. Normalized history must remain traceable to user evidence. A valid source span is useful for auditing but does not prove the model interpreted it correctly.

Allow user corrections without restarting. Preserve superseded findings while the encounter exists. Changing clinical history marks prior assessments outdated and requires regeneration for a current result. Never silently rewrite an earlier assessment.

User confirmation means “this summary reflects what I reported.” It is not clinical verification.

8. Adaptive questioning

Ask one focused question, or a small related group, at a time. Support free text, optional suggested answers, “not sure,” “something else,” and declining to answer.

Clarify ambiguous symptoms and timelines before assigning precise concepts. Cover onset, progression, location, character, severity, associated features, relevant negatives, medications, allergies, medical history, exposures, and contextual risks as appropriate to the encounter.

Select follow-up questions according to unresolved information that could change the assessment or urgency. Avoid asking already answered questions unless clarification is necessary. Do not require a full generic checklist for every complaint.

The interview can stop when the captured information supports a useful provisional assessment, when further questioning has diminishing value, or when the user chooses to stop. Preserve outstanding questions and label incomplete histories honestly. Model confidence alone must not determine completeness.

Allow the engine to return “I need more information” or “I cannot produce a useful estimate from this history.” Do not force diagnoses to fill a fixed-length array.

Store concise action reasons and evidence references where useful. Do not request, expose, or store hidden chain-of-thought.

9. Urgent findings and failure behavior

Check potentially urgent information from the first message and after subsequent answers or corrections. A concerning report should interrupt routine questioning and prominently direct the user toward appropriate urgent help without requiring completion of the interview.

Implement an application-owned safety policy using explicit screening answers, structured findings, and model-extracted flags as inputs. A positive explicit trigger must not be cleared by a reassuring model narrative.

Keep any seeded rules versioned, source-documented, and labeled as unvalidated development content unless actual clinical review has occurred. Do not present keyword matching, hand-written rules, or another LLM as a validated triage system.

Handle negation, uncertainty, historical events, third-person statements, and corrected answers explicitly. Unresolved urgent findings stay visible. If an assessment is shown, its common explanations must not suppress the warning or imply that a dangerous condition has been excluded.

Absence of a triggered alert must never become “you are safe,” “no emergency,” or “you do not need medical care.” The software cannot establish those conclusions from a negative screen alone.

Emergency contact information comes from deployment locale configuration. Use generic local-emergency wording until configured; never guess a country from the model.

On timeout, malformed safety output, or provider failure, retain the history and show that the assessment is incomplete. Never fail into a reassuring result or reuse an outdated assessment as though it were current.

10. Provisional differential diagnosis

Generate a concise ranked list of plausible explanations when the information supports one. This is a user-facing feature and must not require a physician account or approval before viewing.

For each item include:

* A plain-language name and clinical term when helpful.
* A short explanation of why it is being considered.
* Supporting reported findings, referenced to actual clinical facts.
* Relevant conflicting findings.
* Important missing information or limitations.

Keep potential urgency separate from diagnostic ranking. Explain when an examination or testing may be needed to distinguish possibilities, without issuing orders or treatment instructions.

Do not display invented probability percentages or translate model confidence into disease probability. Avoid definitive diagnoses, unsupported “ruled out” claims, and fixed reassurance labels.

Every asserted user fact must reference captured evidence. Do not invent literature citations. If reference retrieval is not implemented, say the explanation is model-generated and omit fabricated sources.

Validate the complete assessment before display. Do not stream unchecked partial diagnoses into the user interface. Progress indicators may stream.

11. Experimental notice and review status

Show a concise warning at onboarding, above the assessment, and in every export. Use this substance:

“Experimental AI assessment — not reviewed by a healthcare professional. This application collects your history and estimates possible explanations for your symptoms. It can be wrong or miss serious illness. This is not a confirmed diagnosis. Discuss the report with a qualified healthcare professional, and do not use it as the sole reason to delay care or start, stop, or change treatment. If you believe you have an emergency, seek local emergency care immediately. Use at your own discretion.”

Record acknowledgment of a specific notice version. Keep a persistent, unobtrusive experimental/unreviewed label during the workflow; do not force repeated blocking dialogs for every answer.

All MVP assessments remain not_clinician_reviewed. Reading, acknowledging, user-confirming, downloading, or printing does not change this status. Omit a “mark clinically reviewed” button in the MVP.

Keep notices and report status under application control so model output cannot remove or override them.

12. Reports and encounter management

Provide a readable report containing:

* Chief concern and chronological history.
* Relevant medications, allergies, and background.
* Reported positives and explicitly stated negatives.
* Missing information, declined questions, and contradictions.
* Whether the user confirmed the summary.
* Provisional differential and concise evidence summaries.
* Urgency notices actually shown during the encounter.
* Experimental and unreviewed labels.
* Creation time, history revision, assessment version, and provider/model identity.

Implement both a versioned JSON export and a print layout suitable for browser Save as PDF. Do not label JSON as FHIR compliant unless actually implemented and validated. Native PDF generation and FHIR can follow later.

Downloading requires authentication. Do not create public report links or send reports externally.

Deletion removes encounter clinical content, model responses, and related sensitive audit content from primary storage. Retain only a minimal nonclinical deletion event if necessary. Explain backup retention limits and previously downloaded copies. Do not claim forensic erasure of every copy.

13. Security and privacy

Implement password hashing, secure session handling, login throttling, CSRF protection where relevant, server-side authorization, input limits, output escaping, security headers, and parameterized database access.

Default Compose exposure to loopback; keep PostgreSQL private. Document TLS reverse proxy deployment and avoid default passwords. Protect operational endpoints from disclosing configuration or clinical data.

Never store API keys or clinical content in frontend bundles, URLs, browser localStorage, ordinary application logs, stack traces, or analytics. Keep sensitive reports out of persistent browser caches. Operational logs should use nonclinical event IDs and timing/status information.

Use supported libraries for cryptography. Protect persisted credentials and clinical payloads at rest with documented key management, or explicitly document required deployment-level encryption rather than falsely claiming it is implemented. Include backup and restore instructions with key-recovery implications.

Only the authenticated operator can configure model endpoints. Permit deliberately configured local/private inference addresses, while preventing user text or model output from choosing destinations. Apply endpoint allowlisting, redirect controls, and protections against unintended metadata-service requests. Do not break local inference by blanket-blocking private addresses.

Treat user text and pasted records as untrusted data. It cannot override policy, extract secrets, change providers, execute tools, or disable warnings. Escape model-generated markup and test prompt-injection attempts.

15. Verification

Write meaningful tests for clinical data integrity, security, and workflow behavior. Do not equate software test success with medical validity.

Include unit and integration tests for:

* Unknown findings staying unknown and negatives requiring explicit evidence.
* Invalid evidence references and malformed model output being rejected.
* Contradictions and user corrections.
* History revisions invalidating existing assessments.
* Duplicate submissions, late responses, and restart/resume behavior.
* Provider timeout, rejection, malformed output, and cancellation.
* No silent provider fallback or demo substitution.
* Prompt injection, escaped markup, endpoint configuration, and protected exports.
* Warnings and unreviewed status surviving every export.
* Encounter deletion and absence of sensitive data in ordinary logs.

Use browser end-to-end tests on the rebuilt application for setup, provider configuration, interview, history correction, results, export, resume, deletion, and failure recovery. Exercise mobile and desktop layouts.

Add a separate synthetic clinical evaluation harness with approximately 15–20 authored cases: straightforward symptoms, vague language, incomplete history, contradictions, medication uncertainty, and concerning presentations. Include positive, denied, historical, and third-person variants of selected warning statements.

In simulated interviews, the interviewer must not receive the hidden reference diagnosis or unrevealed facts. The simulated user should reveal facts only when asked or when the case specifies volunteering them.

Measure fact extraction, unsupported findings, captured key history, contradictions, specified alert behavior, and interview length separately. Report diagnostic comparisons as exploratory. Keep deterministic software regression tests distinct from probabilistic live-model evaluations.

Where feasible, compare free-text-only input with the adaptive history using the same downstream diagnostic model. Do not use an LLM judge as the sole correctness standard or claim synthetic scores prove clinical performance.

Live API checks use synthetic inputs and run only when suitable credentials are available. Clearly distinguish fixture tests from actual provider calls. Document untested providers honestly.
